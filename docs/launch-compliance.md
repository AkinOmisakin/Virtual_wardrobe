# Launch compliance

What both stores require before Cher can ship, and where each piece lives.

Cher uploads photos of people's bodies and sends them to a third-party AI
provider. That is the part reviewers will look at hardest, so the data
disclosures need to be accurate rather than boilerplate.

## Account deletion

Both stores require deletion to be reachable from inside the app, without
contacting support. Play additionally requires a **web** route for people who
have already uninstalled — that is what `legal/delete-account.html` is for, and
its URL goes in the Play Console listing.

The flow:

1. [delete_account_dialog.dart](../lib/pages/delete_account_dialog.dart) makes
   the user type `DELETE`. Everything removed is unrecoverable — there are no
   backups on the Supabase free tier — so a mis-tap must not be enough.
2. [account_service.dart](../lib/services/account_service.dart) calls the
   `delete-account` edge function. Deleting an auth user needs the service role,
   so this cannot be done client-side.
3. [delete-account/index.ts](../supabase/functions/delete-account/index.ts)
   purges storage, then rows, then the auth user — in that order, deliberately:
   - **Storage first, and abort if it fails.** An orphaned bucket of someone's
     body photos with no account left to trace them to is the worst possible
     outcome, so a storage failure leaves the account intact and retryable.
   - **Auth user last**, because it is the only irreversible step: once it is
     gone the caller can no longer prove who they were in order to retry.
4. [20260811000200_account_deletion.sql](../supabase/migrations/20260811000200_account_deletion.sql)
   deletes all rows in one transaction, so a mid-way failure cannot leave a
   half-erased account.

Storage listing is recursive and paged — clothing images live two levels deep
(`<user>/<category>/<file>`) and the list endpoint is one level at a time, so a
naive single call would silently leave photos behind.

## Privacy policy

`legal/` is a static site; deploy it to Cloudflare Pages (free) or GitHub Pages
and put the resulting URLs in the Play Console listing and in
`PRIVACY_POLICY_URL` in `.env`. The Privacy item in the profile menu stays
hidden while that variable is blank, so the app never shows a dead link.

Replace before publishing:

- `[[DATE]]`
- `[[YOUR NAME OR COMPANY]]`
- `[[CONTACT EMAIL]]` (appears several times, including a `mailto:` in
  `delete-account.html`)

The draft describes the real data flows — the AI processors, what leaves the
device, what deletion actually removes. It is not legal advice; have someone
check it if you can.

## Play Data safety form

Answer it consistently with the policy or the listing gets rejected. Based on
what the app actually does today:

| Question | Answer |
| --- | --- |
| Collects personal info? | Yes — email, name (sign-in) |
| Collects photos? | Yes — clothing images and an optional photo of the user |
| Photos shared with third parties? | **Yes** — Replicate and Anthropic process them |
| Data encrypted in transit? | Yes |
| Users can request deletion? | Yes — in-app and via the web page |
| Data used for advertising or tracking? | No |
| Data sold? | No |

"Shared with third parties" is the answer people get wrong. Sending an image to
an inference API counts.

## Generative AI content

This is the policy that actually applies to Cher, and it applies **regardless of
whether the app has a social feed**: an app that generates content with AI must
disclose that in the app experience and let users flag offensive output without
leaving the app.

Both are implemented:

- **Disclosure** — a "Generated by AI" label under every try-on result, and an
  AI marker on saved try-on posts.
- **Reporting** — a Report action next to both, opening
  [report_dialog.dart](../lib/pages/report_dialog.dart). Categories are
  deliberately explicit, with `minor` kept separate from `sexual` so the
  highest-severity reports can be triaged first — for an app that renders
  clothing onto photos of people, that is the case that matters most.

Reports land in `content_reports`. Under RLS they are insert-only from the
client: a user can file one and read back their own, but never read, edit, or
retract anyone else's. Triage happens in the Supabase dashboard with the service
role — a manual path is acceptable at this scale, but you do need to actually
look at the queue:

```sql
select created_at, reason, content_type, content_url, details
  from content_reports where status = 'open' order by created_at;
```

## Not applicable: user-to-user reporting and blocking

Cher has **no cross-user visibility**. Every query in the app filters by the
current user; `posts` are only ever read back with `.eq('user_id', userId)`, and
the follower/following counts on the profile are hardcoded placeholders. Nobody
can see anyone else's content, so there is nothing to block and no third-party
content to report.

If a feed or profile browsing is ever added, this changes immediately and the
full UGC obligations apply: blocking, reporting other users' content, and terms
prohibiting uploads of people without their consent.

## Worth fixing before launch

The `Clothing images` bucket is served with `getPublicUrl()`, so those images are
readable by anyone holding the URL. Model photos correctly use signed URLs. It
is not a review blocker, but a public bucket sits awkwardly next to a privacy
policy that says photos are not shared — consider moving it to signed URLs too.
